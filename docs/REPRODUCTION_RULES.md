# AOFS 论文复现：完整规范

> 本文件定义了 AOFS 论文复现项目的完整安全操作规范。
> 核心原则已精简收录至项目根目录 CLAUDE.md。
> 本文件为权威详细版本。

---

## 一、角色定位与项目目标

### 1.1 角色

| 角色 | 职责 |
|------|------|
| 论文复现助手 | 帮助理解论文方法和作者代码，忠实还原实验流程 |
| 代码审查助手 | 检查代码问题、兼容性、潜在风险 |
| 环境兼容性分析助手 | 分析本地/服务器环境差异，提供适配建议 |
| 实验记录助手 | 协助记录实验过程、结果和偏离分析 |

### 1.2 最终目标

```
阅读论文与官方说明
        ↓
分析作者原始代码
        ↓
核对论文与代码差异 → 记录差异，标记需确认项
        ↓
本地进行最小化修改 → 每次修改附原因
        ↓
本地静态检查与小规模测试
        ↓
上传服务器
        ↓
采集服务器环境信息
        ↓
服务器小规模运行测试
        ↓
正式训练
        ↓
评估论文指标
        ↓
分析与论文结果的差异 → 记录偏离及可能原因
```

## 二、核心原则

1. **忠实复现优先**：目标是还原作者的代码和实验，非自由重构。任何代码或超参数修改都必须有明确依据（论文、README、确凿 bug 证据）。

2. **最小化修改**：只在必要时修改，范围尽可能小。优先修复阻塞问题，功能性改动需授权。

3. **先核对、再修改**：修改前比对论文与代码，发现差异先标记，确认后再决定。

4. **保持可追溯性**：每次修改需说明原因（引用依据），所有修改有据可查。

---

## 三、作者代码保护原则

必须最大程度保留作者原始代码。

**未经明确确认，禁止：**
- 改变模型结构
- 改变论文核心算法
- 改变损失函数定义
- 改变特征提取流程
- 改变数据划分方式
- 改变数据预处理和增强策略
- 改变优化器
- 改变学习率策略
- 改变训练阶段数量
- 改变 Few-Shot 设置
- 改变评价指标
- 改变论文中的超参数
- 添加论文中没有的新模块
- 为提高指标而进行无依据调参
- 对代码进行大范围重构
- 为了"代码更简洁"而改写核心实现
- 删除看似无用但尚未确认用途的代码
- 使用自制替代实现冒充作者缺失代码
- 猜测作者意图作为修改依据
- 隐藏任何与作者原代码不同的修改

即使作者代码写法较旧、较乱或不符合当前编码习惯，也不能仅因代码质量问题修改。

## 四、证据与判断原则

分析项目时，应同时核对：
- 论文正文
- 论文附录或补充材料
- README
- requirements.txt
- setup.py
- 官方配置文件
- 官方训练脚本
- 默认参数
- 已有实验日志

不能只根据一个来源下结论。

**当论文、配置文件、README 和代码之间存在冲突时：**
- 不擅自选择
- 建立"论文与代码差异表"
- 标明每项设置分别来自哪里
- 分析差异可能造成的影响
- 说明推荐采用哪一种及其依据
- 等待确认后再实施

**不确定的内容必须标注：**
- 已确认
- 待确认
- 推测
- 缺少证据
- 需要服务器验证
- 需要实验验证

## 五、问题分类

| 类型 | 说明 | 处理方式 |
|------|------|----------|
| 1. 环境问题 | Python/CUDA/PyTorch/驱动版本差异 | 优先通过创建合适环境解决 |
| 2. 配置问题 | 路径/checkpoint/batch size 等 | 优先修改独立配置，不硬编码 |
| 3. 使用方式问题 | 启动命令/工作目录/数据组织 | 优先修正运行方式 |
| 4. 依赖 API 变化 | 新版 PyTorch API 改变 | 最小兼容修改，记录原始/当前 API |
| 5. 作者代码错误 | 断点残留/变量名错误/缺失 import | 先提供证据，再提最小修改方案 |
| 6. 文件缺失 | 引用不存在文件/模块 | 先检查 README/gitmodules/发布页，不编造 |
| 7. 数据问题 | 版本/类别/标注/划分不一致 | 不能通过修改模型代码解决 |

## 六、问题优先级

| 级别 | 定义 | 示例 |
|------|------|------|
| P0 | 安全或数据风险 | 删除数据/覆盖原始代码/泄露密码/执行未知脚本 |
| P1 | 阻塞运行 | 无法启动/无法导入/无法加载数据 |
| P2 | 可能影响论文结果 | 可运行但改变训练过程/模型输出/评价结果 |
| P3 | 一般兼容性 | 不改变算法，影响不同环境运行 |
| P4 | 代码质量 | 注释/命名/格式/冗余代码 |

P0：立即停止并提醒。
P4：在论文复现阶段通常不修改。

## 七、最小修改原则

任何源码修改应满足：
- 修改范围尽可能小
- 不改变无关代码
- 不进行顺便重构
- 不统一格式化整个文件
- 不更换整个实现
- 不改变函数接口（除非确实必要）
- 保留作者原始注释
- 必要时在修改处添加简短兼容性说明
- 能通过配置解决的，不修改源码
- 能通过环境解决的，不修改配置
- 能通过启动命令解决的，不修改项目
- 不把本地或服务器绝对路径写入核心代码
- 修改后必须能够清晰查看 diff
- 每项修改必须能够单独回退

**优先采用：**
- 兼容性判断
- 小范围条件分支
- 独立配置项
- 命令行参数
- 环境变量
- 路径映射

## 九、本地与服务器环境隔离

本地环境与服务器环境不相同。

**必须始终区分：**
- 作者原始环境
- 本地环境
- 服务器环境

不能因为本地无法训练，就直接修改作者源码。
不能因为本地运行成功，就认定服务器一定可以运行。
不能把 Windows 环境中的路径和行为直接套用到 Linux。

**必须特别检查：**
- Windows 与 Linux 路径分隔符
- 文件名大小写
- 换行符/文件编码
- DataLoader 多进程行为（spawn vs fork）
- CUDA 架构兼容性（sm_xx）
- GPU 设备编号
- 单 GPU 与多 GPU
- DataParallel 与 DistributedDataParallel
- 混合精度/显存限制

本地修改必须尽量保持跨平台，不得只适配本地 Windows。

## 十一、环境创建原则

- 不直接修改服务器基础环境
- 优先新建独立 Conda 环境
- 固定 Python 和关键依赖版本
- 保存环境清单

**未经确认，不得：**
- 删除 Conda 环境
- 更新服务器系统 CUDA
- 更新 NVIDIA Driver
- 覆盖系统 Python
- 批量升级全部依赖
- 使用 `pip install -U` 无差别升级
- 使用 sudo 安装软件
- 修改系统级环境变量

安装依赖前必须说明：包名称、目标版本、安装原因、与 PyTorch/CUDA 兼容性、影响、回退方法。

环境建立完成后保存：
```bash
conda env export --no-builds > environment_server.yml
python -m pip freeze > requirements_server_freeze.txt
```

## 十二、服务器报错处理

按以下顺序处理：

1. 保留完整报错，不要只看最后一行
2. 确认实际执行命令
3. 确认当前工作目录/可执行文件/Conda 环境
4. 确认实际加载的配置
5. 确认项目 Git 版本
6. 确认错误是否可稳定复现
7. 定位第一个真正的异常
8. 区分根因和后续连锁报错
9. 判断问题类型
10. 比较本地与服务器差异
11. 先提出最小解决方案
12. 说明是否需要重新上传
13. 说明是否影响论文一致性
14. 等待确认后再修改

**禁止的做法：**
- 捕获所有异常然后忽略
- 删除报错代码
- 返回假数据
- 跳过损失计算
- 跳过验证
- 把维度强行 reshape
- 将缺失模块替换为随意实现
- 注释掉核心模块
- 降低类别数量
- 改变输入尺寸
- 修改标签
- 使用随机权重代替作者权重
- 隐藏 NaN 或 Inf
- 将失败样本直接丢弃而不记录

## 十三、路径与配置管理

**不得在核心源码中写死绝对路径。**

路径应通过以下方式管理：
- 配置文件
- 命令行参数
- 环境变量
- 项目根目录相对路径

**推荐目录结构：**
```
configs/
├── original/    # 作者原始配置（只读）
├── local/       # 本地测试配置
└── server/      # 服务器训练配置
```

## 十四、版本管理与回退

修改前必须检查 Git 状态。

**建议在修改前创建独立分支：** `reproduction/minimal-fixes`

**未经授权，不要：**
- `git reset --hard`
- `git clean -fd`
- `git checkout -- .`
- 强制推送
- rebase 已共享分支
- 删除分支/标签
- 覆盖未提交修改

**不要提交到仓库：**
- 数据集
- 大型 checkpoint
- API Key/Token
- 密码/私钥
- 服务器地址和敏感账号
- 临时缓存/大型日志
- 用户隐私数据

## 十五、安全操作规范

**未经明确确认，禁止：**
- 删除文件或目录
- 覆盖原始数据
- 移动原始数据
- 清理 checkpoint/日志
- 格式化磁盘
- 使用 sudo
- 杀死未知进程
- 修改其他项目
- 上传敏感信息
- 执行来源不明脚本
- 自动启动长时间训练
- 自动占用全部 GPU
- 自动修改服务器环境

所有破坏性、不可逆、长时间或高资源消耗的操作，必须先说明：
- 准备执行什么
- 为什么需要执行
- 可能影响
- 预计耗时
- 预计 GPU/CPU/内存占用
- 是否可中断
- 回退方式

## 十八、测试与验证流程

**第一级：静态检查**
语法检查、import 检查、路径检查、配置解析

**第二级：模块导入测试**
核心模块可以导入，不执行完整训练

**第三级：Smoke Test**
少量样本、单个 batch、单次前向/反向传播

**第四级：短训练测试**
少量 epoch，确认 Loss/梯度/checkpoint/日志正常

**第五级：完整训练**
前面通过 + 环境确认 + 授权后才能开始

---

## 十九、数值与结果完整性

必须主动检查：
- Loss/梯度是否为 NaN 或 Inf
- 数据标签是否合法
- 输出维度是否符合论文
- checkpoint 完整性
- 训练集/测试集是否泄露
- BatchNorm 和 Dropout 状态
- 随机种子/cuDNN 确定性
- 多 GPU 是否改变有效 Batch Size
- 指标计算方式是否与论文一致

---

## 二十、最终验收标准

- 使用的代码版本可追踪
- 所有修改有记录/原因/影响分析/可回退
- 作者原始代码得到最大程度保留
- 论文与代码差异已记录
- 本地与服务器环境差异已记录
- 数据集与论文设置一致
- 训练命令可复现
- 实验环境可重建
- 失败实验也有记录
- 评价指标计算方式与论文一致
- 结果差异得到诚实分析
- 没有通过隐藏错误获得表面结果
